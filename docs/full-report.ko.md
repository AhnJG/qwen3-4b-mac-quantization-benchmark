## 실험 설계

`Qwen/Qwen3-4B-Instruct-2507`을 네 가지 설정으로 실행해 숫자로 비교합니다. GGUF F16을 넣은 이유가 있습니다. "엔진 효과"와 "4비트 효과"를 나눠 보기 위해서입니다. 이게 없으면 "GGUF Q4_K_M vs HF FP16" 비교에서 실행 엔진(transformers 또는 llama.cpp)과 숫자 정밀도가 동시에 바뀌어서 원인을 가를 수 없습니다.

|  | HF transformers 엔진 | llama.cpp 엔진 |
|---|---|---|
| **FP16/F16 정밀도** | HF FP16 (기준) | GGUF F16 |
| **4비트로 줄이기(양자화)** | HF NF4 (bitsandbytes) | GGUF Q4_K_M |

- 표를 가로(행)로 비교하면 엔진 효과(`GGUF-F16 / HF-FP16`)이고, 세로(열)로 비교하면 4비트 효과(`GGUF-Q4_K_M / GGUF-F16`)입니다.
- 지표: 최대 메모리(Peak VRAM, HF만), 생성 속도(decode tok/s), TTFT, 토큰별 시간의 p50/p90/최댓값, WikiText-2 perplexity(네 설정 모두)
- 입력 길이를 128→4096 토큰으로 바꿔 가며 쟀습니다.

## 실행 방법

**로컬 (Apple Silicon, MPS/Metal)** — 이 보고서의 실측치는 이 경로(Apple M3)에서 나왔습니다.
```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
CMAKE_ARGS="-DGGML_METAL=on" pip install --no-cache-dir --force-reinstall llama-cpp-python

# caffeinate -i 필수: 잠자기는 벽시계 타이밍을 조용히 망칩니다(v5가 8시간 중 6시간 잠들어 폐기됨)
caffeinate -i python benchmark_quantization.py --stage context_sweep --repeats 5                  # 24GB 대조군
caffeinate -i python benchmark_quantization.py --stage context_sweep --repeats 5 --ballast-gb 8   # 16GB 기계
python benchmark_quantization.py --stage perplexity                                               # 네 설정 전부

python tools/audit.py --repeats 5   # 신뢰성 게이트: 잠자기·불완전 셀·타이밍 불일치 검사
python tools/analyze.py             # 보고서의 모든 수치를 원자료에서 재생성
python tools/figures.py             # README 그림 2장 재생성
python tools/cliff_probe.py --probe {prompt|sdpa|steps|cache|alloc|residue}   # 스톨 진단
python tools/output_agreement.py    # 네 설정의 greedy 출력이 어디서 갈리는지
```

`--ballast-gb N`은 메모리를 일부러 차지하는 프로그램(ballast)이 압축되지 않은 메모리 N GB를 실행 내내 붙잡게 합니다. 그러면 **호스트보다 작은 기계 등급을 재현**할 수 있습니다. 이 24GB M3 Air에서 `8`은 16GB 맥, `16`은 8GB 맥에 해당합니다. M3 Air는 8/16/24GB 구성의 **대역폭(100GB/s)이 같습니다**. 그래서 메모리 양만 줄이는 이 방식이 16GB 기기를 가깝게 흉내 낼 것으로 봅니다. 다만 실제 16GB 기기와 비교해 확인하지는 않았고, 완전히 같지도 않습니다([한계](#한계)).

**로컬 (CUDA GPU)**: `requirements.txt`를 설치한 뒤 `pip install llama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cu124`를 실행합니다. (⚠️ CUDA로 교차 검증한 데이터는 아직 v1의 버그 있는 방식으로 잰 것뿐입니다 — [한계](#한계).)

### ⚠️ 메모리가 큰 기계에서는 결과가 다르게 나올 수 있습니다

이 저장소의 핵심 결과는 세 가지입니다. HF 경로의 멈춤, FP16 @2048 "절벽", 그리고 필요할 때 파일에서 읽어 오는 방식(mmap)을 쓰는 그룹과 메모리에 계속 올려 두는 그룹(상주 그룹)이 두 무리로 확실히 나뉘는 것입니다. 이 셋은 **이 기기에서 메모리 부족이 걸린 상태에서 관측됐습니다.** 원인에 대한 가설은 "HF가 토큰을 만들 때마다 GPU 드라이버가 잡고 있는 메모리를 기계의 물리 한계까지 밀어 올린다"는 것입니다(관측과 맞지만 증명되지는 않음). **메모리가 넉넉하면 나타나지 않을 것으로 예상합니다(검증하지 않음).**

- **64GB 이상 맥 (예상, 검증하지 않음)**: 멈춤 배율이 1.0x에 가깝게 나오고, HF와 GGUF의 격차가 줄며, 절벽은 보이지 않을 것입니다. 그렇게 나와도 이 보고서의 설명을 뒤집는 결과가 아니라, 예측과 맞는 결과입니다.
- **재현하려면 용량을 줄이세요**: `--ballast-gb N`으로 쓸 수 있는 메모리를 **24GB 이하**로 맞춘 뒤 비교하십시오. 64GB 기계라면 `--ballast-gb 40`(=24GB)과 `--ballast-gb 48`(=16GB)이 이 보고서의 두 조건에 해당합니다.
- **확인 방법**: `tools/analyze.py`의 "정상 속도 vs 멈춤 포함" 표에서 멈춤 배율이 모두 1.0x에 가깝다면 메모리 부족의 영향이 작았을 가능성이 큽니다. 다만 이 지표만으로 메모리 부족이 없었다고 판정할 수는 없습니다(「한계」의 멈춤 배율 설명 참고). 그런 경우 **계산 속도와 정밀도 결과는 비슷하게 나오고 멈춤과 메모리 결과만 사라질 것으로 예상합니다(검증하지 않음).**

바꿔 말하면 이 벤치마크는 두 층으로 보입니다. 메모리 부족이 약하면 주로 계산 효율을 비교하는 것이고, 메모리 부족이 크면 메모리를 잡는 방식의 차이가 함께 드러납니다(둘을 완전히 나눈 것은 아닙니다). 어느 쪽을 재고 있는지는 멈춤 배율 열을 보면 알 수 있습니다.

결과는 `results/results.jsonl`에 한 줄씩 덧붙습니다(append). 각 줄에는 `device`/`prompt_tokens`/`n_new`/`repeat`/`max_new_tokens`와 **`started_at`/`ended_at`/`swap_used_gb`/`ballast_gb`**가 기록됩니다. 그래서 실행이 잠자기나 스왑 포화로 오염됐는지 나중에 증명할 수 있습니다(v5에는 타임스탬프가 없어서 증명할 수 없었습니다). 여러 용량의 실행이 한 파일에 섞여도 `ballast_gb`로 나눌 수 있습니다.

v7부터 `step_ms_p50`/`step_ms_p90`/`step_ms_max`가 추가됐고, v8부터 `step_ms`(토큰별 시간 배열 전체)와 `schema`가 추가됐습니다. 배열을 통째로 남기는 이유가 있습니다. 요약값 세 개만으로는 **"셀의 퍼짐이 우연한 잡음인지 구조인지"를 나중에 물을 수 없기** 때문입니다. v7이 즉석 대표값 계산 방식(`min-p50`, 최솟값 방식)에 기대다가 [철회](estimator-bias-note.ko.md)한 근본 원인이 이것입니다. **v8 이전 행(현재 200행 전부)에는 `step_ms`가 없습니다**(다시 재지 않았습니다).

`tokens_per_sec`는 총시간 기반 **평균**이라서 드문 멈춤이 값을 좌우합니다. 반면 `step_ms_p50`은 정상 속도(토큰 하나를 만드는 보통 시간, 중앙값)를 잽니다. 둘의 격차가 곧 **멈춤 배율**입니다. 이렇게 나누지 않으면 "계산이 느리다"와 "몇 번 멈췄다"를 구분할 수 없습니다. v3·v5·v6·v7 측정이 이 구분 없이 [절벽을 네 번 재현](measurement-history.ko.md)했습니다. 메모리 부족을 만드는 도구는 `tools/ballast.py`, `tools/pressure_probe.py`이고, 멈춤 진단 도구는 `tools/cliff_probe.py`입니다.

## 결과

측정 환경: Apple M3 MacBook Air (24GB 통합 메모리, 100GB/s). HF는 PyTorch MPS, GGUF는 llama.cpp Metal을 썼습니다. 아래는 입력 128 토큰, **5회 반복의 중앙값**입니다(v7, 24GB 기준 조건). TTFT는 입력을 넣고 첫 토큰이 나올 때까지 걸린 시간입니다.

| 방식 | 최대 메모리 (Peak VRAM, GiB) | 생성 속도 (tok/s) | TTFT (s) | Perplexity |
|---|---|---|---|---|
| HF FP16 (기준) | 7.54 | 9.74 | 0.48 | 9.5413 |
| HF NF4 (bitsandbytes) | 2.88 | 3.48 | 0.67 | 9.8060 |
| GGUF F16 (llama.cpp) | –\* | 11.31 | 0.43 | **9.5417** |
| GGUF Q4_K_M (llama.cpp) | –\* | 31.92 | 0.46 | **9.7446** |

입력 128에서는 네 설정 모두 멈춤 배율이 1.0x라서 평균과 정상 속도가 같습니다(토큰 하나하나가 튀는 경우는 여기서도 있습니다 — [단서](#입력-길이에-따른-변화)). 입력이 긴 구간은 다릅니다 — [입력 길이에 따른 변화](#입력-길이에-따른-변화)를 보세요.

\* llama.cpp는 torch식 VRAM API가 없어 재지 못했습니다.

**v7에서 네 설정 모두 perplexity를 구했습니다.** v1–v6은 HF만 재고, GGUF는 "llama.cpp 자체 구현이라 비교 불가"로 비워 두었습니다. 그런데 그건 llama.cpp의 perplexity *도구*를 쓸 때의 이야기였고, 본질적인 한계가 아니었습니다. `llm._scores`로 로짓을 직접 받아서, **네 설정이 같은 토큰열(HF 토크나이저)을 같은 윈도우 순서로 같은 채점 함수에 넣으면** 그대로 비교할 수 있습니다(WikiText-2 test 전체, 299,078토큰 / 584윈도우).

두 가지가 이 수치를 뒷받침합니다.

- 새 채점 방식이 **v1의 HF 내부 loss 방식 수치를 5자리까지 같게 재현**합니다(FP16 9.54129 → 9.5413, NF4 9.80603 → 9.8060).
- 서로 독립인 두 F16 경로가 **9.5413 vs 9.5417로 0.005% 차이**로 만납니다.

### 출력이 얼마나 같은가

perplexity는 전체를 묶은 지표라서, 두 모델이 같은 값을 내면서도 다른 답을 할 수 있습니다. 네 설정에 같은 프롬프트 4개를 greedy로 60토큰씩 만들게 하고, **토큰 단위로 어디서 갈라지는지** 봤습니다.

| FP16과 비교 | P0 | P1 | P2 | P3 | |
|---|---|---|---|---|---|
| **GGUF F16** | 동일 | 동일 | 동일 | 동일 | **4/4 완전일치** |
| GGUF Q4_K_M | 동일 | 15 | 0 | 12 | 1/4 |
| HF NF4 | 3 | 53 | 11 | 5 | 0/4 |

(숫자 = 갈라진 첫 토큰 위치)

**두 F16 경로의 출력 텍스트가 네 프롬프트 모두에서 일치합니다.** 완전히 다른 두 구현이 같은 가중치 정밀도에서 같은 답을 냈다는 뜻입니다. perplexity의 0.005% 차이와는 별개로, 이 결과도 **엔진 차이는 성능(속도)에서 나고 수치(결과값)에서는 나지 않는다**는 쪽을 뒷받침합니다.

> **초판 정정 — 이 테스트는 "토큰 단위로 같다"를 보이지 못합니다.** `tools/output_agreement.py`는 HF에서는 생성된 토큰 ID를 바로 받습니다. 그런데 GGUF에서는 텍스트로 되돌렸다가 **다시 토큰으로 바꿔서** 비교합니다(BPE를 왕복하면 원래 토큰열로 돌아온다는 보장이 없습니다). 또 길이가 다르면 `zip`이 짧은 쪽에서 멈춥니다. 그래서 **한쪽이 다른 쪽의 앞부분이기만 해도 "동일"로 판정**합니다. 초판의 "240토큰 전부에서 토큰 단위로", "비트 수준으로 같은 결정"이라는 표현은 이 스크립트가 뒷받침할 수 있는 것보다 강한 주장이었습니다(검토 B6).

두 4비트 방식은 둘 다 일찍 갈라지고, **서로 간에는 우열이 뚜렷하지 않습니다**(Q4_K_M이 P0·P3에서, NF4가 P1·P2에서 FP16에 더 가깝습니다). 갈라지는 위치는 엄격한 지표입니다. greedy 디코딩은 토큰 하나가 달라지면 그 뒤가 통째로 달라집니다. 그래서 "3번째에서 갈라짐"이 "답이 나쁘다"를 뜻하지는 않습니다. 품질 순위는 perplexity(Q4_K_M +2.13% vs NF4 +2.77%)로 매기는 것이 맞습니다. 이 표는 **F16 두 경로가 같다는 것**을 확인하는 용도입니다.

### 엔진 효과와 4비트 효과 나눠 보기

**정상 속도 배율**(= `p50(분모) / p50(분자)`, p50은 반복 5회의 중앙값)을 입력 길이별로 적고, 기하평균도 냈습니다. `python tools/analyze.py`가 이 표를 출력합니다.

| 24GB | 128 | 512 | 1024 | 2048 | 4096 | **기하평균** |
|---|---|---|---|---|---|---|
| 엔진만 바꿈 `GGUF-F16 / HF-FP16` | 1.16 | 1.22 | 1.30 | 1.49 | 1.19 | **1.27배** |
| 4비트로 바꿈 `Q4_K_M / GGUF-F16` | 2.84 | 2.70 | 2.60 | 2.46 | 2.35 | **2.58배** |
| NF4로 바꿈 `HF-NF4 / HF-FP16` | 0.36 | 0.38 | 0.39 | 0.46 | 0.44 | **0.40배 (2.48배 느림)** |
| 둘 다 바꿈 `Q4_K_M / HF-FP16` | 3.30 | 3.29 | 3.40 | 3.67 | 2.79 | **3.28배** |

| 16GB | 128 | 512 | 1024 | 2048 | 4096 | **기하평균** |
|---|---|---|---|---|---|---|
| 엔진만 바꿈 | 1.17 | 1.48 | 1.76 | 3.49 | 1.51 | **1.74배** |
| 4비트로 바꿈 | 2.87 | 2.52 | 2.63 | 2.44 | 2.21 | **2.53배** |
| NF4로 바꿈 | 0.36 | 0.44 | 0.54 | 1.09 | 0.44 | **0.53배 (1.90배 느림)** |
| 둘 다 바꿈 | 3.34 | 3.73 | 4.63 | 8.53 | 3.33 | **4.40배** |

> **엔진 효과는 입력 길이에 따라 1.16~1.49배(24GB)로 달라집니다. 입력 길이 하나만 골라 대표값으로 쓰면, 그것 자체가 대표값 계산 방식을 고르는 일이 됩니다.**

"GGUF가 FP16보다 3.28배 빠르다"는 말은 그대로 유지됩니다. 그런데 요인을 나눠 보면 대부분(2.58배)이 K-quant 방식의 4비트 줄이기이고, 엔진 자체의 기여는 1.27배입니다.

같은 "4-bit"인데 결과가 정반대입니다. llama.cpp의 K-quant는 2.58배 빨라지고, bitsandbytes NF4는 2.48배 느려집니다. 이유는 이렇게 보입니다. K-quant는 추론 전용으로, 4비트 값을 원래 숫자로 되돌리는 계산(디퀀타이즈)과 행렬곱을 한 코드로 합친 방식입니다. NF4는 QLoRA 학습 때 메모리를 아끼는 것이 주목적입니다. 그래서 추론할 때는 디퀀타이즈하는 부담이 메모리 읽기량 절감분을 서로 지웁니다. 다만 GPU 코드를 직접 분석해 확인한 것이 아니라, 구조에 대한 지식을 바탕으로 한 추정입니다.

**품질까지 보면 NF4가 설 자리가 없어집니다.** v6까지의 요약은 "메모리는 줄지만 속도 대가를 치른다"였습니다. 이제 두 4비트 방식을 같은 기준으로 잴 수 있습니다.

| | 속도 (입력 128) | Perplexity | F16 대비 품질 손실 |
|---|---|---|---|
| GGUF Q4_K_M | **31.92 tok/s** | **9.7446** | **+2.13%** |
| HF NF4 | 3.48 tok/s | 9.8060 | +2.77% |

**K-quant(Q4_K_M)가 NF4보다 빠르면서 품질 손실도 더 작습니다.** 얼마나 빠른지는 재는 방법에 따라 다릅니다.

- 입력 128 기준, 평균 처리량: 9.2배
- 정상 속도의 기하평균: 8.1배
- 입력 길이별: 6.3~9.2배

두 축 모두에서 NF4가 집니다. 메모리 절감은 NF4가 62%(7.54→2.88GB)로 분명합니다. GGUF Q4_K_M도 가중치가 ~2.5GB로 같은 수준입니다(torch식 API가 없어 재지 못했을 뿐입니다).

즉 **llama.cpp Q4_K_M과 비교하면, 추론에서 bitsandbytes NF4를 고를 이유가 이 실험 조건 안에서는 속도로도 perplexity로도 없습니다**(HF FP16과 비교하면 NF4가 메모리를 62% 줄이고, 16GB @2048에서는 오히려 빠릅니다). NF4의 설계 목적이 QLoRA *학습*의 메모리 절감이라는 점을 생각하면 놀랄 일은 아닙니다. 다만 v6까지는 "속도를 잃고 메모리를 얻는 교환"으로 보였습니다. v7에서 Q4_K_M과 견주어 보니 **교환이 아니라 열세**였다고 정정합니다.

### 입력 길이에 따른 변화

입력 128→4096 토큰에서의 생성 속도(tok/s)입니다. **24GB 기준 조건, 5회 반복 중앙값 [최소–최대]**:

| 입력 | HF FP16 | HF NF4 | GGUF F16 | GGUF Q4_K_M |
|---|---|---|---|---|
| 128 | 9.74 [9.49–9.78] | 3.48 [3.26–3.51] | 11.31 [7.62–11.40] | 31.92 [24.79–32.06] |
| 512 | 7.68 [7.11–9.24] | 3.47 [3.32–3.47] | 11.13 [10.58–11.18] | 30.03 [21.27–30.27] |
| 1024 | 7.30 [6.24–8.21] | 3.23 [3.14–3.38] | 10.83 [10.77–10.94] | 27.58 [21.47–28.46] |
| 2048 | **2.16** [1.48–2.44] | 2.98 [2.54–3.23] | 9.71 [7.44–10.11] | 22.90 [14.92–25.54] |
| 4096 | 5.55 [2.78–5.90] | 2.43 [2.27–2.57] | 7.92 [7.04–9.45] | 19.13 [12.71–20.92] |

**이 표에는 두 가지가 섞여 있습니다.** `tokens_per_sec`는 총시간 기반 평균이라서, 계산이 느린 것과 몇 번 멈춘 것을 구분하지 못합니다. 나누어 보면 이렇습니다.

| 방식 | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| **HF FP16** | 9.75/9.74 `1.0x` | 9.16/7.68 `1.2x` | 8.32/7.30 `1.1x` | **6.51/2.16 `3.0x`** | 6.90/5.55 `1.2x` |
| **HF NF4** | 3.49/3.48 `1.0x` | 3.47/3.47 `1.0x` | 3.21/3.23 `1.0x` | 2.98/2.98 `1.0x` | 3.05/2.43 `1.3x` |
| **GGUF F16** | 11.34/11.31 `1.0x` | 11.18/11.13 `1.0x` | 10.84/10.83 `1.0x` | 9.73/9.71 `1.0x` | 8.22/7.92 `1.0x` |
| **GGUF Q4_K_M** | 32.18/31.92 `1.0x` | 30.13/30.03 `1.0x` | 28.25/27.58 `1.0x` | 23.90/22.90 `1.0x` | 19.28/19.13 `1.0x` |

각 칸은 `정상 속도(1000/토큰 시간 p50) / 보고값(평균)`과 **멈춤 배율**입니다. **GGUF는 10칸 전부 1.0x이고, HF만 1.0x를 벗어납니다.**

여기에는 단서가 두 가지 있습니다.

- (a) 배율 1.0x는 "멈춤이 전혀 없었다"가 아니라 **"멈춤을 모두 합쳐도 평균을 움직이지 못했다"**는 뜻입니다. `--probe alloc`의 정의(한 토큰 시간이 그 실행 p50의 3배 초과)를 적용하면 24GB GGUF 3개 칸에 그런 토큰이 있습니다. 가장 심한 것은 `Q4_K_M ctx=512`의 652.9ms(p50 33.8ms의 **19.3배**)입니다.
- (b) 이 열은 **한 실행 안에서** p50과 평균을 비교하기 때문에 **반복 간 흔들림을 보지 못합니다.** 24GB `Q4_K_M @2048`은 p50이 39.1~69.0ms(1.77배)로 흔들리는데, 다섯 실행 모두 배율이 1.0x입니다.

입력 처리 시간인 TTFT는 네 설정 모두 입력 길이에 거의 비례합니다. 그래서 4096에서 14~17초로 모입니다(C-1 수정 검증: 버그가 있던 v2는 HF TTFT를 0.03초로 보고했는데, 4104토큰을 처리하는 데는 물리적으로 불가능한 값이었습니다).

**"% 저하"도 함정이고, 평균 기반 절대 지연도 함정입니다.** 입력 128→4096에서 토큰당 늘어난 시간(ms)을 세 가지 방식으로 계산하면 이렇습니다.

| 방식 | 평균 기반 | p50 중앙값 | p50 최솟값 방식 (철회, 참고용) | p50 평균 |
|---|---|---|---|---|
| HF FP16 | +77.5 | **+42.4** | +42.1 | **+45.6** |
| HF NF4 | +124.3 | **+41.4** | +41.9 | **+46.8** |
| GGUF F16 | +37.9 | +33.5 | +17.6 | +26.2 |
| GGUF Q4_K_M | +21.0 | +20.8 | +16.7 | +26.2 |

**24GB HF 쌍은 중앙값·평균 기준 모두 격차가 작습니다**(중앙값 +0.9ms, 평균 −1.2ms). 이것이 이론상 예측입니다. 토큰당 읽는 바이트는 가중치 + KV 캐시(앞 토큰 정보를 담아 두는 메모리)입니다. **KV 캐시가 늘어나는 양은 가중치 정밀도와 상관없습니다.** 그러므로 입력 길이가 더하는 절대 비용도 같아야 합니다.

단, **"격차가 작다"와 "격차가 0임을 확인했다"는 다릅니다.** 신뢰구간(참값이 있을 법한 범위, 부트스트랩으로 계산)을 `analyze.py`에 구현하고 나서야 보인 점입니다. HF 쌍의 신뢰구간은 p50 중앙값 기준 **[−36.0, +21.0] ms**로 넓습니다. 0을 포함하므로 이론상 예측과 모순되지 않지만, 36ms짜리 격차도 배제하지 못합니다. n=5의 한계입니다. **예측에 부합한다**까지가 이 데이터로 할 수 있는 말입니다.

**24GB GGUF 쌍은 그렇지 않습니다.** 격차가 p50 중앙값 기준 12.7ms, 평균 기준 0.0ms로 갈립니다(철회된 최솟값 방식으로는 0.9ms). 모두 같은 데이터에서 나온 값입니다. p50 중앙값 기준 부트스트랩 95% 신뢰구간(20,000회)은 **[−24.7, +31.5] ms**이고, **현재 표본으로는 판정 불가**입니다. 이 데이터로는 판단할 수 없습니다.

원인은 GGUF F16 @4096 칸의 반복 간 흔들림입니다(p50 105.0~140.6ms). 이 칸에서 최솟값을 고르면 13.7% 줄어드는데, 입력 128에서는 0.9%만 줄어듭니다. 그 결과 **늘어난 시간을 계산할 때 −15.9ms의 순수한 줄어듦이 남습니다.** HF 쌍은 두 끝(입력 128과 4096)에서 줄어드는 정도가 같아서(0.7%/0.7%) 이 값이 움직이지 않습니다. 결정적으로, **이 칸에서 `min`이 고른 실행은 다섯 중 스왑이 가장 높았던 실행(10.0GB, 나머지는 4.5~5.9GB)**입니다. 그래서 "빠른 실행 = 덜 오염된 실행"이라는 전제 자체가 성립하지 않습니다.

16GB는 반대입니다.

- **GGUF 쌍은 격차가 작습니다.** 중앙값 기준 +17.6/+17.0, 평균 기준 +16.6/+17.2이고, 중앙값 기준 신뢰구간은 [−8.8, +8.9]입니다.
- HF 쌍은 흔들립니다. 중앙값 기준 +56.4/+71.9입니다.

정리하면 **네 쌍 모두 부트스트랩 신뢰구간이 0을 포함합니다.** 격차가 작게 나온 두 쌍(24GB HF, 16GB GGUF)은 이론상 예측에 **부합**하지만, 같다고 확인한 것은 아닙니다. 나머지 둘은 이 데이터로는 판단할 수 없습니다. 24GB에서 HF 쌍의 증가(+41~47ms)가 GGUF 쌍(+21~34ms)보다 큰 것은 중앙값·평균 점추정 모두에서 유지됩니다. 하지만 n=5로 검정한 차이는 아닙니다.

> **v7 초판의 서술을 철회합니다.** 초판은 `p50 최소` 열만 굵게 처리하고 "오염을 걷어낸 마지막 열에서 두 정밀도가 일치합니다"라고 적었습니다. `p50 중앙값` 열을 **같은 표에 찍어 놓고도** 그 열이 반증하는 결론을 옆 열로 선언한 것입니다. 외부 검토가 이를 "여섯 번째 결함 — 이번엔 코드도 지표도 아닌 **대표값 계산 방식**"이라고 지적했습니다(v7 검토 A1). `min`은 치우친 대표값 계산 방식이고, 그 치우침이 결론에 유리한 쪽으로만 작동했습니다.

같은 구간의 최대 메모리(Peak VRAM, HF만, 중앙값)는 FP16 7.54 → 8.22GiB (+0.68), NF4 2.88 → 3.92GB (+1.04)입니다. NF4의 절대 증가가 더 큰 이유는 v1부터 밝혀지지 않았습니다([한계](#한계)).

## 16GB: 많이 쓰는 메모리 크기

24GB에서는 FP16 모델(8GB)이 들어가서, 벤치마크가 주로 계산 효율을 잽니다(그래도 HF 생성은 메모리 한계에 닿고, FP16@2048은 멈춤 배율이 3.0x입니다). 많이 쓰는 구성인 16GB에서는 다릅니다. 같은 방식으로 `--ballast-gb 8`을 걸어 다시 쟀습니다(5회 중앙값 [최소–최대]).

| 입력 | HF FP16 | HF NF4 | GGUF F16 | GGUF Q4_K_M |
|---|---|---|---|---|
| 128 | 9.69 [8.99–9.70] | 3.48 [3.26–3.51] | 11.11 [10.41–11.41] | 32.17 [28.89–32.27] |
| 512 | 5.63 [4.98–7.97] | 3.28 [2.95–3.46] | 11.08 [10.25–11.14] | 28.06 [22.74–30.47] |
| 1024 | 5.38 [4.21–7.72] | 3.36 [2.62–3.39] | 10.87 [9.65–10.92] | 28.55 [26.57–28.59] |
| 2048 | **0.37** [0.33–0.58] | 3.24 [2.65–3.26] | 10.34 [9.65–10.36] | 25.52 [21.98–25.68] |
| 4096 | 2.41 [0.66–2.85] | 1.14 [0.02–1.38] | 9.24 [8.80–9.54] | 20.82 [17.37–21.12] |

**같은 데이터를 정상 속도 / 평균 / 멈춤 배율로 나눠 보면 원인이 드러납니다.**

| 방식 | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| **HF FP16** | 9.77/9.69 `1.0x` | 7.56/5.63 `1.3x` | 6.22/5.38 `1.2x` | **3.00/0.37 `8.1x`** | 6.30/2.41 `2.6x` |
| **HF NF4** | 3.50/3.48 `1.0x` | 3.30/3.28 `1.0x` | 3.38/3.36 `1.0x` | 3.26/3.24 `1.0x` | 2.80/1.14 `2.4x` |
| **GGUF F16** | 11.39/11.11 `1.0x` | 11.19/11.08 `1.0x` | 10.97/10.87 `1.0x` | 10.48/10.34 `1.0x` | 9.49/9.24 `1.0x` |
| **GGUF Q4_K_M** | 32.63/32.17 `1.0x` | 28.22/28.06 `1.0x` | 28.79/28.55 `1.0x` | 25.61/25.52 `1.0x` | 21.00/20.82 `1.0x` |

**24GB 대비 저하율(평균 기준):**

| 방식 | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| HF FP16 | −0% | −27% | −26% | **−83%** | **−57%** |
| HF NF4 | −0% | −5% | +4% | +9% | **−53%** |
| GGUF F16 | −2% | −0% | +0% | +7% | +17% |
| GGUF Q4_K_M | +1% | −7% | +4% | +11% | +9% |

**mmap 그룹이냐 상주 그룹이냐에 따라 두 무리로 확실히 나뉩니다.** 입력 길이 전 구간에서 가장 나쁜 저하는 mmap 그룹이 **−6.6%**, 상주 그룹이 **−82.8%**입니다. 연속으로 이어지지 않고 두 덩어리이며, 그 사이에 아무것도 없습니다. 다만 이 구분은 엔진 구분(llama.cpp vs HF)과 정확히 겹칩니다. 그래서 이 측정만으로는 메모리를 쓰는 방식의 효과를 엔진의 다른 차이와 나눌 수 없습니다.

**"3배 가벼운 모델이 진다"는 것은 16GB에서만 나오는 결과가 아닙니다.** GGUF F16(가중치 8GB)이 HF NF4(가중치 2.9GB)를 이기는 것은 맞습니다. 하지만 정상 속도로 보면 그 배수는 **메모리 용량과 상관없이 ~3.3배로 같습니다**:

```
NF4가 GGUF-F16보다 느린 배수 (정상 상태 p50)
        ctx=128   512  1024  2048  4096
24GB     3.25   3.22  3.37  3.27  2.70
16GB     3.25   3.39  3.25  3.21  3.39
```

**24GB에서도 똑같이 집니다.** 그래서 원인은 "메모리를 잡는 전략"이 아니라 **bitsandbytes NF4가 Metal용 빠른 코드를 충분히 지원받지 못하는 것**으로 보입니다(추정, GPU 코드 단위 분석은 하지 않음). 이는 [README](../README.ko.md) 결과 1과 같은 이야기입니다. 순위를 정하는 것은 가중치 크기가 아니라 **4비트 형식에 대한 빠른 코드 지원**입니다.

메모리 용량이 영향을 주는 곳은 한 군데입니다. 같은 배수를 **평균 처리량**으로 보면 16GB @4096에서만 3.4배가 **8.1배**로 벌어집니다(단, NF4@4096은 점검에서 반복 간 흔들림이 크다고 표시된 칸입니다). 즉 메모리 부족은 격차를 *만들지* 않고, **멈춤을 통해 키울** 뿐입니다.

**그리고 v7은 그 이유가 계산 속도가 아님을 보여 줍니다.** 8GB를 빼앗겼을 때 두 엔진에서 벌어지는 일이 질적으로 다릅니다.

| | 정상 속도 24GB → 16GB | 멈춤 배율 |
|---|---|---|
| GGUF F16 @2048 | 9.73 → **10.48** (+7.7%) | 1.0x |
| GGUF F16 @4096 | 8.22 → **9.49** (+15%) | 1.0x |
| HF FP16 @2048 | 6.51 → **3.00** (반토막) | **8.1x** |
| HF FP16 @4096 | 6.90 → 6.30 | 2.6x |

**llama.cpp의 계산 속도는 메모리 부족에 거의 반응하지 않습니다.** 16GB의 10개 칸 전부 멈춤 배율이 1.03x 이하이고, 정상 속도는 24GB 대비 −6%~+15%로 반복 간 잡음 범위 안에서 움직입니다(오히려 빨라진 칸도 있습니다). HF는 두 번 맞습니다. 정상 속도 자체가 무너지고, 그 위에 멈춤이 얹힙니다.

유력한 이유는 **언제 메모리를 잡느냐**입니다(엔진의 다른 차이와 나뉘지 않은 해석). llama.cpp는 불러올 때 KV 캐시를 `n_ctx`만큼 통째로 예약하고, 가중치는 mmap으로 읽습니다(llama.cpp의 표준 동작이며, 이 저장소에서 GGUF 경로의 메모리는 재지 않았습니다). 그래서 생성 도중 메모리 부담을 **더 만들지 않을 것으로 보입니다**. 반면 HF는 토큰 하나를 만들 때마다 72번씩 메모리를 다시 잡습니다. 그 과정에서 torch의 MPS 할당자가 GPU 드라이버가 잡고 있는 메모리를 생성마다 24.9GiB(≈ 물리 RAM, FP16 진단 실험 기준)까지 밀어 올립니다([측정 이력](measurement-history.ko.md)). **즉 HF 쪽은 메모리 부족을 견디는 것이 아니라 스스로 만들고 있을 가능성이 있습니다(가설).**

이것은 v4의 mmap A/B(mmap을 켠 것과 끈 것의 비교)가 시사한 것과는 **다른, 두 번째로 가능한 원인**입니다(역시 가설). v4는 *가중치* mmap이 메모리가 부족할 때 중요하다는 것을 시사했습니다(8GB 기계 조건, 칸당 1회: `use_mmap`을 끄면 저하가 −9.2% → −39.8%). v7의 `--probe cache`에서는 *KV 캐시*를 미리 잡아 두자 멈춤이 사라졌습니다(설정당 2회, 정상 속도도 함께 바뀌어 깔끔한 비교는 아님). 두 몫을 나누려면 토큰별 시간 기록을 붙여서 mmap A/B를 다시 돌려야 합니다([남은 질문](#남은-질문)).

상주 그룹 *안에서* 가중치 크기가 작용하는 곳은 **멈춤이 언제 시작되느냐**입니다. FP16(8GB)은 2048부터, NF4(2.9GB)는 4096에서 무너집니다. 계산 속도 순위는 크기가 정하지 않습니다(위 참조). 크기는 **메모리가 부족할 때 멈춤이 시작되는 시점**과 함께 움직이는 것으로 보입니다(두 설정의 비교일 뿐이라 검증된 인과는 아닙니다).

**이론상 예측은 16GB에서 엔진에 따라 갈립니다.** v6은 "스왑이 시작되면 다른 물리 법칙"이라고 적었지만, 평균 기반이라 그렇게 보인 부분이 큽니다. 입력 128→4096에서 토큰당 늘어난 시간은 이렇습니다.

- 16GB **GGUF 쌍은 중앙값·평균 기준 +17~18ms로 격차가 작습니다**(중앙값 기준 부트스트랩 신뢰구간 [−8.8, +8.9]).
- **HF 쌍은 대표값 계산 방식에 따라 갈립니다**(p50 중앙값 기준 +56.4/+71.9ms). 그래서 이 표본으로는 판정 불가입니다([입력 길이에 따른 변화](#입력-길이에-따른-변화)).

**실사용 관점 — 16GB에서 150토큰 생성에 걸리는 전체 시간(입력 처리 포함):**

| | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| **GGUF Q4_K_M** | 5s | 7s | 9s | 14s | 24s |
| **GGUF F16** | 14s | 15s | 17s | 21s | 32s |
| HF NF4 | 43s | 47s | 48s | 53s | 144s |
| HF FP16 | 16s | 28s | 31s | **412s** | 76s |

16GB 맥에서 transformers FP16으로 2K 프롬프트를 처리하면 **실행별 4.4~7.7분**(중앙값 기준 약 7분)이 걸립니다. 같은 작업이 llama.cpp Q4_K_M으로는 **14초**입니다. 다섯 번 중 네 번은 이 중 약 231–363초가 계산이 아니라 멈춰 있던 시간으로 추정됩니다(생성 시간에서 '토큰 수 × 그 실행의 정상 속도'를 뺀 값이며, 직접 잰 값은 아닙니다). 이 칸은 점검에서 반복 간 흔들림이 크다고 표시된 칸이므로, 한 숫자가 아니라 범위로 읽어야 합니다.

## 메모리 부족 실험 (ballast)

v1은 "다른 앱이 켜져 있어 스왑으로 붕괴"라는, 다시 만들 수 없는 일화로 "GGUF는 mmap 덕분에 강건하다"고 주장했습니다. v2에서 이를 통제 실험으로 만들었습니다(ballast 프로세스로 메모리를 강제로 차지하고, mmap을 켠 것과 끈 것을 비교). 그런데 결함이 두 가지 드러났습니다.

- (a) `ballast.py`가 처음에 메모리를 채운 뒤 64MB 창만 다시 쓰는 순회 버그가 있었습니다. 그래서 나머지 ~99%가 스왑으로 밀려나 실제 메모리 부족을 유지하지 못했습니다.
- (b) 0GB 기준선이 이미 스왑 30GB로 오염돼 있었습니다. "여유 vs 부족"이 아니라 "부족 vs 더 부족"이었습니다.

v3에서 도구를 완전히 고쳤습니다.

- `ballast.py` 순회 버그를 고쳤습니다. 모든 페이지를 매 주기 건드려 메모리에 계속 올려 둡니다(3GB를 요청했을 때 RSS가 줄지 않고 유지됨을 확인했습니다).
- `pressure_probe.py`에 **GGUF F16을 추가**했습니다(8GB 가중치로 메모리 부족에 가장 약한 후보입니다).
- **설정 순서를 무작위로 섞었습니다**(순서 때문에 결과가 섞이는 것을 없애기 위해서입니다).
- **측정하는 시점마다 실제 스왑 사용량을 기록**합니다(메모리 부족이 실제로 걸렸는지 확인하기 위해서입니다).
- 여러 단계의 ballast(0/8/16GB)로 효과가 나야 하는 조건을 일부러 넣은 대조군(양성 대조)을 만들었습니다.
- v3에서 고친 측정 경로(`measure_one`)를 썼습니다.

**v4에서 재부팅 직후(스왑 0GB) `tools/pressure_probe.py --ballast-gb 0,8,16`을 실행했습니다**(`results/results_memory_pressure.jsonl`). ballast 0→16GB(= 8GB 기계)에서 생성 속도(tok/s)가 떨어진 정도입니다.

| 방식 | 입력 128 | 입력 4096 |
|---|---|---|
| GGUF Q4_K_M **(mmap)** | 30.96 → 31.02 (+0.2%) | 20.89 → 18.96 (**−9.2%**) |
| GGUF Q4_K_M **(nommap)** | 30.32 → 30.28 (−0.1%) | 20.74 → 12.49 (**−39.8%**) |
| GGUF F16 (mmap) | 11.09 → 10.63 (−4.1%) | 9.39 → 8.14 (−13.4%) |
| HF FP16 | 9.16 → 8.73 (−4.6%) | 2.44 → 0.97 (−60.4%) |
| HF NF4 | 3.49 → 3.41 (−2.4%) | 2.38 → 0.47 (−80.5%) |

- **짧은 입력(128)에서는 아무도 크게 흔들리지 않습니다**(≤5%). 한꺼번에 쓰는 메모리가 작아서, 메모리 부족은 긴 입력에서만 문제가 됩니다.
- **긴 입력(4096)에서 mmap 가설을 뒷받침하는 결과가 나왔습니다(칸당 1회 측정).** 같은 Q4_K_M 가중치와 엔진에서 `use_mmap`만 끄면 저하가 **−9.2% → −39.8%로 4.3배** 커집니다. 0GB에서는 둘 다 ~20.8 tok/s로 같으므로, 이 격차는 메모리가 부족할 때만 생깁니다. **v2의 버그 있던 ballast가 "반증"했던 v1의 mmap 가설이, 고친 도구와 깨끗한 기준선에서 다시 지지된 셈입니다.** 다만 메인 측정에서 같은 칸(Q4_K_M@4096, 24GB)의 반복 간 범위가 12.71~20.92 tok/s입니다. 그러므로 1회 측정의 격차는 반복해서 확인해야 합니다.
- **이 `use_mmap` A/B는 메인 측정이 대신할 수 없는 유일한 증거입니다.** 메인 측정에서는 mmap을 끌 수 없습니다. 그래서 "GGUF가 강건한 건 llama.cpp라서가 아니라 메모리를 잡는 전략 때문"이라는 주장을 가장 직접 겨냥한 대조군은 여기에만 있습니다. 다만 이 표에는 **토큰별 시간 기록이 없어서**, 저하가 계산이 느려진 것인지 멈춤인지 나중에 나눌 수 없습니다. v7이 남긴 가장 큰 미완입니다([남은 질문](#남은-질문) 2번).

**⚠️ 이 표 전체가 칸당 1회 측정입니다(n=1).** 특히 HF 수치는 표본을 늘려 가며 다시 재 보니, 두 경로의 순위가 **한 번 뒤집혔다가 결국 붙었습니다**:

| 입력 4096, 24GB→16GB | v4 (n=1) | v6 (n=3) | v7 (n=5) |
|---|---|---|---|
| HF FP16 | −66.2% | −80% | **−57%** |
| HF NF4 | −74.6% | −41% | **−53%** |

(v4 열은 ballast 0→8GB 값입니다. 정정 전에는 위 표의 0→16GB 값(−60.4%/−80.5%)이 잘못 들어가 있었습니다.)

v4만 보면 "NF4가 FP16보다 더 무너진다"로, v6만 보면 "FP16이 두 배 더 무너진다"로 읽힙니다. 그러나 **n=5에서는 −57% vs −53%로 사실상 구분되지 않습니다.** 이 칸은 멈춤 배율이 2.6x·2.4x로 둘 다 높습니다. 그래서 여기서 재는 것은 계산 속도가 아니라 그날의 멈춤 운입니다. **값이 가까운 두 설정의 순위를 이런 칸에서 매기면 안 된다는 사례로 남깁니다.** 표본을 늘릴 때마다 결론이 바뀌었고, 세 번째에서야 "차이 없음"이 드러났습니다.

방향성 있는 결론은 [16GB 절](#16gb-많이-쓰는-메모리-크기)에 있습니다. 계산 속도 순위는 4비트 형식에 대한 빠른 코드 지원이 정하는 것으로 보입니다(NF4가 GGUF F16보다 24GB에서 3.2배, 16GB에서 3.3배 느림 — 기하평균). 가중치 크기는 메모리가 부족할 때 **멈춤이 언제 시작되느냐**와 함께 움직입니다(FP16 2048, NF4 4096).

("0GB" 기준선도 8GB F16 가중치를 불러오면서 세션 스왑이 6~7GB로 오릅니다. 하지만 측정마다 스왑을 기록해서 이를 드러냈고, mmap A/B는 두 설정의 스왑이 비슷해서 공정합니다.)

## 한계

- **함께 실행된 프로그램.** 일상 사용 환경에 가깝게 측정 중 Chrome과 Claude 앱을 일부러 켜 두었지만, 얼마나 쓰였고 메모리를 얼마나 차지했는지는 기록하지 않았습니다. 첫 측정 직후 스왑이 이미 4.46GB(24GB 조건), 5.74GB(16GB 조건)였으므로, 모델이 실제로 쓸 수 있던 메모리는 명목상 조건보다 적었을 가능성이 큽니다. 아래의 "24GB 조건도 메모리 부족이 없는 상태가 아니다"는 설명에도 이 프로그램들의 몫이 섞여 있어, HF 경로 자체의 몫과 나눌 수 없습니다. 네 방식은 같은 시간대에 무작위 순서로 측정해 서로의 비교는 비교적 안전하지만, 멈춤의 크기와 16GB 조건의 절대 시간은 영향을 받았을 수 있습니다.
- **llama.cpp 쪽 토큰 세기.** 스트리밍으로 받은 조각 하나를 토큰 하나로 셌습니다. 조각 하나에 토큰이 여러 개 들어갈 수 있어 transformers의 토큰 단위와 정확히 같다는 보장은 없습니다. 실제로 llama.cpp 측정 30회는 150개가 아니라 149개로 세어졌습니다. 149와 150의 차이만 따지면 속도 계산의 분자가 1% 미만 달라지지만, 조각과 실제 토큰의 대응과 시각은 복원할 수 없어서 이것이 llama.cpp 쪽 속도·정상 속도 오차의 상한은 아닙니다.
- **품질 지표의 범위.** 품질은 WikiText-2 perplexity(다음 단어 예측)만 쟀습니다. 답변의 정확도나 지시 수행 능력은 평가하지 않았습니다.
- **두 "4비트"의 비트 수.** Q4_K_M은 일부 가중치를 6비트로 남기고, NF4는 임베딩층과 출력층을 16비트로 둡니다. 가중치당 평균 비트 수는 재지 않았습니다. 이 차이는 품질 차이(+2.13% 대 +2.77%)의 일부 원인으로 의심됩니다. 속도 차이의 주된 원인일 가능성은 낮습니다. transformers 4비트는 비트를 훨씬 많이 쓰는 llama.cpp 16비트보다도 느렸기 때문입니다.
- **두 메모리 조건은 차례로 측정했습니다.** 네 방식은 같은 시간대 안에서 무작위 순서로 측정했지만, 24GB(15:30–16:47)와 16GB(16:59–21:05)는 번갈아 돌리지 않고 차례로 돌렸습니다. 그래서 두 조건의 차이에는 8GB를 추가로 차지한 효과와 다른 프로그램의 부하 변화가 섞여 있습니다.
- **측정은 메모리 부족이 없는 환경에서 돌린 것이 아닙니다. 다만 "시간이 갈수록 포화된다"는 예전 서술은 틀렸습니다.** v1부터 이 항목은 "8GB 모델을 반복해서 불러오고 내리면서 파일 페이지 캐시가 통합 메모리를 채운다"고 추정해 왔습니다. v7 초판은 그 자리에 `--probe residue`의 "반환되지 않는 16.35GB 풀"을 넣으면서 스왑이 **"3.6 → 13.2GB로 올랐다"**고 적었습니다. **그 두 숫자는 최솟값과 최댓값이지 처음과 마지막이 아닙니다**(`audit.py`가 `min → max`를 출력합니다). 측정 순서대로 보면 꾸준히 늘어나는 흐름은 없습니다:

  ```
  ballast 0:  첫 4.46 → 마지막 5.76 GB   측정순서와의 Spearman = −0.047
  ballast 8:  첫 5.74 → 마지막 7.46 GB   측정순서와의 Spearman = −0.090
  ```

  v8에서 `--probe residue`를 MB 단위, 8회로 다시 돌려서 이 불일치를 풀었습니다(`results/probe_residue.log`):

  ```
  1회차 잔여 (풀 확보)      16930 MB
  2회차 이후 측정당 잔여    −27.4 MB   (범위 −192 ~ +32 MB, n=7)
  생성 중 최고 driver 보유   24.90 GiB  (≈ 이 기계의 물리 RAM)
  ```

  **누수가 아니라 고원(더 쌓이지 않고 평평해진 상태)입니다.** 첫 HF 측정이 16.4GB 풀을 확보하고 돌려주지 않지만, 그 뒤로는 쌓이지 않습니다(2회차 이후 순잔여가 음수). 진단 실험 기록과 측정 기록이 이제 같은 말을 합니다. **메모리 부족은 실제로 있고 크지만, 시간이 지나도 쌓이지는 않습니다.**

  실제로 스왑을 좌우하는 것은 시간이 아니라 **바로 앞에서 어느 설정이 돌았는지**입니다(24GB 스왑 중앙값: FP16 10.2 / GGUF_F16 10.0 / NF4 9.5 / Q4_K_M 5.8 GB). 전체 순서 섞기는 여전히 필요합니다. 시간에 따른 쏠림 때문이 아니라 **설정끼리 서로 영향을 주는 것**을 흩뜨리기 위해서입니다. 그리고 **"24GB 기준 조건"은 메모리 부족이 없는 상태가 아닙니다.** HF가 생성할 때마다 물리 RAM 한계에 닿기 때문입니다.
- **멈춤 배율(1000/p50 ÷ 평균 tok/s)은 틀리게 읽힐 수 있는 경우가 네 가지 있습니다.** 정상 속도(절대 p50)와 함께 읽어야 하고, 이것 하나만으로 결론을 내면 안 됩니다.
  1. **1.0x가 두 가지 상태를 뜻합니다.** "매끄럽게 빠름"과 "고르게 죽어 있음"입니다. 후자의 예가 16GB NF4@4096의 한 실행입니다(150토큰에 **127분**, p50 **69.9초**).
  2. **나쁜 실행일수록 1.0에 가까워지고, 결국 그 아래로 내려갑니다.** 같은 칸의 실행별 배율은 `[0.73, 2.16, 2.17, 2.55, 2.58]`이고, 0.73이 그 127분짜리입니다. 사각지대가 아니라 **거꾸로 가는 관계**입니다.
  3. **표에 찍히는 값은 "비의 중앙값"이 아니라 "중앙값의 비"입니다**(`analyze.py`가 `median(p50)`과 `median(tok/s)`를 따로 구해 나눕니다. 서로 다른 실행에서 온 두 수입니다). 16GB FP16@2048의 실행별 배율은 `[0.92, 4.62, 6.12, 10.27, 10.31]`이라 중앙값이 6.12인데, 표에는 **8.11**이 찍힙니다.
  4. **반복 간 흔들림을 보지 못합니다.** 한 실행 안의 두 통계를 비교하므로, 실행 전체가 함께 움직이면 1.0x가 유지됩니다. 24GB `Q4_K_M @2048`은 p50이 1.77배 흔들리는데 다섯 실행 모두 1.0x입니다.

  더 나은 지표가 이미 데이터에 있습니다. `step_ms_p90 / step_ms_p50`은 "느린 쪽 상위 10% 토큰이 중앙값의 몇 배인가"를 직접 재고, 위 네 가지 중 셋에 걸리지 않습니다. `python tools/analyze.py`의 「멈춤 형태 — p90/p50」 표가 이 값을 출력합니다.
- **CUDA 교차 검증 데이터는 v1의 버그 있는 방식으로 잰 것이라 뺐습니다**(`results/archive/results_cuda_t4_colab_v1_double_prefill_bug.jsonl`). C-1 문제는 CUDA도 비동기라 똑같이 나타나므로, 지금 방식으로 다시 재야 유효합니다. **지금 결론은 전부 Apple Silicon 통합 메모리 기준**입니다. mmap의 이점이 별도 VRAM을 가진 GPU에서도 성립하는지는 검증하지 않았습니다.
- **모델 크기는 실험 설계 때문에 정해졌습니다.** 2×2 구성에서 FP16 쪽이 성립하려면 FP16 가중치가 16GB에 들어가야 합니다. 4B(~8GB)가 그 조건을 만족하는 가장 큰 크기입니다(7B는 ~14GB, 8B는 ~16GB라서 불가). 그래서 **실사용자가 16GB에서 실제로 돌릴 구성(7~14B의 4비트)과는 다릅니다.** 이 보고서의 목적은 요인을 나눠 보는 것이지, 기종별 최적 모델을 추천하는 것이 아닙니다.
- **MPS 최대 메모리(Peak VRAM)는 20ms 간격으로 확인한 근사값**이라 짧은 튐을 놓칠 수 있습니다. NF4의 절대 VRAM 증가가 FP16보다 큰 이유는 밝혀지지 않았습니다.
- **GGUF 경로는 측정마다 워밍업 후 `llm.reset()`으로 캐시를 비워서** 매번 입력 전체를 처음부터 처리하게 합니다. 앞부분이 재사용되는 실제 여러 턴 대화보다 보수적인(불리한) 조건입니다.
- **속도 지표는 전체 시간(end-to-end)을 잰 것이고, GPU 코드 단위로 분석한 것이 아닙니다.** NF4가 느린 이유(디퀀타이즈 코드를 하나로 합치지 않음)는 구조에 대한 지식을 바탕으로 한 추정입니다.

## 남은 질문

이 저장소는 v8에서 측정을 마쳤습니다. 아래는 데이터가 답하지 못하고 남은 질문입니다.

1. **GPU 드라이버가 잡고 있는 메모리의 증가 곡선을 입력 길이별로 측정** — 최우선입니다. `--probe alloc`이 "생성할 때마다 24.9GiB까지 차오르고, 멈춤은 59~69번째 단계에 몰린다"까지 밝혔습니다. 남은 질문은 **증가 속도가 입력 길이에 따라 어떻게 달라지고, 한계를 언제 넘느냐**입니다. 이것이 "왜 2048이 4096보다 심한가"의 답일 가능성이 높습니다(4096은 입력 처리 직후에 한계를 넘어 초반에 몰아서 겪고 회복합니다. 이는 `--probe steps`의 4096 데실(10분위) 패턴과 맞습니다). 촘촘한 입력 길이 측정은 그다음입니다.
2. **토큰별 시간 기록을 붙여서 `pressure_probe`의 mmap A/B 다시 돌리기** — 가중치 mmap과 KV 캐시 미리 잡기 중 어느 쪽이 GGUF의 강건함에 얼마나 기여하는지 나눕니다. 지금 v4 데이터에는 토큰별 시간 통계가 없어서 나중에 나눌 수 없습니다.
3. NF4 디퀀타이즈 부담을 GPU 코드 단위로 분석하기, NF4 VRAM 증가 원인 밝히기(확인 간격을 줄여서 비교).
4. 지금 방식으로 CUDA(Colab T4) 다시 교차 검증 — mmap의 이점이 통합 메모리만의 특징인지 가립니다. **CUDA는 페이징 대신 OOM(메모리 부족 오류)이 나므로, 멈춤 현상 자체가 다르게 나타날 것입니다.**
5. `--ballast-gb 16`(=8GB 기계) — FP16이 아예 못 돌 가능성이 높고, 그것도 결과입니다.
6. Q4_K_M만 7~8B로 넓히기 — 요인 분해는 4B에서 유지하되, 실사용에 가까운 대표성을 얻습니다.
7. GGUF 경로의 메모리 축 — llama.cpp는 torch식 VRAM API가 없어 재지 못했습니다. `Llama(verbose=True)` 로그를 읽어서 채울 수 있습니다.
