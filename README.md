# Efficient AI: On-Device Quantization Benchmark (Qwen3-4B-Instruct)

> **Status: v6.** 측정 코드의 결함을 네 번 잡아 여기까지 왔습니다. v1 이중 `generate()`(prefill이 처리량에 혼입) → v2 그 수정이 또 틀림(MPS 비동기 때문에 `time.time()`이 GPU 완료가 아닌 CPU 도달 시각을 찍어 prefill 재누출) → v3 `sync_device()`로 실측 검증 후 수정 → v4 ballast 도구 수정 후 mmap 가설 재확인 → **v6에서 네 번째 결함을 잡았습니다: 반복을 블록으로 돌린 탓에 스윕 자체가 유발한 메모리 포화가 3회차에 몰려 모든 중앙값을 편향시키고 있었습니다**(v3 −21%, v5 −25%). 전체 셔플로 고쳤고, 검증됐습니다(v6 −4%/+3%, 방향성 소멸).
>
> v6는 또한 **용량을 축으로 추가**했습니다 — 같은 프로토콜로 24GB(대조군)와 16GB(ballast 8GB)를 재서, 주류 구성인 16GB에서 무슨 일이 일어나는지 분리했습니다. 결과는 4비트냐 16비트냐가 아니라 **mmap이냐 상주냐**가 지배한다는 것입니다([16GB](#16gb-실제-사람들이-쓰는-기계)).
>
> 모든 결과 행에 `started_at`/`ended_at`/`swap_used_gb`/`ballast_gb`가 기록되어 **사후 감사가 가능합니다**. 이전 버전 데이터는 `results/*_v1_*.jsonl`, `*_v2_*.jsonl`, `*_v5_*.jsonl`에 감사 기록으로 보존.

## TL;DR

> `Qwen3-4B-Instruct-2507`을 2×2 격자(HF/llama.cpp 엔진 × FP16/4-bit)로, **24GB와 16GB 두 용량에서** 비교했다.
>
> **① 엔진 vs 양자화 분리** (ctx=128, 3회 중앙값): 같은 정밀도에서 llama.cpp 엔진의 이점은 **1.16배**에 불과하지만, 같은 llama.cpp 안에서 K-quant 양자화는 **2.90배**를 낸다 — "GGUF가 3.4배 빠르다"의 실체는 엔진이 아니라 양자화다. 세 번의 독립 실행에서 재현됐다(v3 1.12/2.89, v5 1.06/3.05, v6 1.16/2.90).
>
> **② 같은 4비트가 정반대로 움직인다**: K-quant는 2.90배 빨라지는데 bitsandbytes NF4는 **2.7배 느려진다**(0.370배). K-quant는 디퀀타이즈+행렬곱을 융합한 추론 전용 커널인 반면, NF4는 QLoRA *학습*의 메모리 절감이 목적이라 디퀀타이즈 오버헤드가 대역폭 절감분을 상쇄한다(추정, 프로파일링 미수행). VRAM은 62% 절감(7.54→2.88GB), perplexity 저하는 +2.8%로 미미.
>
> **③ "% 저하"는 함정이다**: 128→4096에서 GGUF F16(−16%)이 Q4_K_M(−36%)보다 강건해 *보이지만*, 토큰당 절대 지연 증가는 **+18.0ms vs +18.6ms로 사실상 같다**. F16은 baseline이 느려 같은 손해가 작은 %로 보일 뿐이다. 대역폭 roofline의 예측대로다(토큰당 읽는 바이트 = 가중치 + KV캐시이고, KV 증가는 정밀도와 무관).
>
> **④ 16GB에서는 mmap이 전부다**: 컨텍스트 전 구간 최악 저하가 mmap 그룹(GGUF) **−12.7%** vs 상주 그룹(HF) **−80.5%**. 연속 스펙트럼이 아니라 두 덩어리로 갈린다. 결정적으로 **GGUF F16(가중치 8GB, mmap)이 HF NF4(가중치 2.9GB, 상주)를 압도한다** — 3배 가벼운 모델이 진다. 모델을 얼마나 줄였느냐보다 런타임이 메모리를 어떻게 잡느냐가 중요하다. 절벽은 FP16이 2048, NF4가 4096에서 시작하고 GGUF는 오지 않는다.
>
> **⑤ roofline은 스왑 전까지만 유효하다**: 16GB에서도 mmap 그룹은 절대 증가가 붙어 있지만(+30.3 vs +27.4ms), 상주 그룹은 규모가 다른 세계로 간다(FP16 +1247ms).
>

## What this is

`Qwen/Qwen3-4B-Instruct-2507`을 네 설정으로 실행해 정량 비교합니다. GGUF F16을 넣은 이유는 "엔진 효과"와 "양자화 효과"를 분리하기 위해서입니다 — 그러지 않으면 "GGUF Q4_K_M vs HF FP16"에서 엔진과 정밀도가 동시에 바뀌어 원인을 가를 수 없습니다.

|  | HF transformers 엔진 | llama.cpp 엔진 |
|---|---|---|
| **FP16/F16 정밀도** | HF FP16 (baseline) | GGUF F16 |
| **4-bit 양자화** | HF NF4 (bitsandbytes) | GGUF Q4_K_M |

- 행 = 엔진 효과 (`GGUF-F16 / HF-FP16`), 열 = 양자화 효과 (`GGUF-Q4_K_M / GGUF-F16`)
- 지표: Peak VRAM(HF만), decode tok/s + TTFT, WikiText-2 perplexity(HF만)
- 컨텍스트 128→4096 토큰 스윕

## Quickstart

**로컬 (Apple Silicon, MPS/Metal)** — 이 README의 실측치는 이 경로(Apple M3):
```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
CMAKE_ARGS="-DGGML_METAL=on" pip install --no-cache-dir --force-reinstall llama-cpp-python

# caffeinate -i 필수: 잠자기는 벽시계 타이밍을 조용히 망칩니다(v5가 8시간 중 6시간 잠들어 폐기됨)
caffeinate -i python benchmark_quantization.py --stage context_sweep --repeats 3                  # 24GB 대조군
caffeinate -i python benchmark_quantization.py --stage context_sweep --repeats 3 --ballast-gb 8   # 16GB 기계
python benchmark_quantization.py --stage perplexity                                               # HF FP16/NF4
```

`--ballast-gb N`은 상주·비압축 메모리 N GB를 실행 내내 붙잡아 **호스트보다 작은 기계 등급을 재현**합니다. 이 24GB M3 Air에서 `8`은 16GB 맥, `16`은 8GB 맥에 해당합니다. M3 Air는 8/16/24GB 구성의 **대역폭(100GB/s)과 코어 수가 동일**하므로 용량만 빼는 이 시뮬레이션은 거친 근사가 아닙니다 — 다만 완전히 같지는 않습니다([Limitations](#limitations)).

**로컬 (CUDA GPU)**: `requirements.txt` 설치 후 `pip install llama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cu124`. (⚠️ CUDA 교차검증은 아직 v1 버그 방식 데이터뿐입니다 — [Limitations](#limitations).)

결과는 `results/results.jsonl`에 append됩니다. 각 줄에 `device`/`prompt_tokens`/`n_new`/`repeat`/`max_new_tokens`와 **`started_at`/`ended_at`/`swap_used_gb`/`ballast_gb`**가 기록되어, 실행이 잠자기·스왑 포화로 오염됐는지 사후에 증명할 수 있습니다(v5에는 타임스탬프가 없어 그게 불가능했습니다). 여러 용량의 실행이 한 파일에 섞여도 `ballast_gb`로 분리됩니다. 메모리 압박 도구는 `tools/ballast.py`, `tools/pressure_probe.py`.

## Results

측정: Apple M3 MacBook Air (24GB unified memory, 100GB/s) · HF는 PyTorch MPS, GGUF는 llama.cpp Metal · 아래는 컨텍스트 128 토큰, **3회 반복의 중앙값**(v6 24GB 대조군).

| Config | Peak VRAM (GB) | decode tok/s | TTFT (s) | Perplexity |
|---|---|---|---|---|
| HF FP16 (baseline) | 7.54 | 9.02 | 0.51 | 9.54 |
| HF NF4 (bitsandbytes) | 2.88 | 3.34 | 0.69 | 9.81 |
| GGUF F16 (llama.cpp) | –\* | 10.45 | 0.45 | n/a\*\* |
| GGUF Q4_K_M (llama.cpp) | –\* | 30.35 | 0.49 | n/a\*\* |

\* llama.cpp는 torch식 VRAM API가 없어 미측정. \*\* GGUF perplexity는 llama.cpp 자체 구현이라 HF loss 기반과 직접 비교 불가.

### 엔진 효과 vs 양자화 효과

|  | 계산식 | 배수 |
|---|---|---|
| 엔진 (F16 고정, 엔진만) | GGUF-F16 / HF-FP16 = 10.45 / 9.02 | **1.16배** |
| 양자화 (llama.cpp 고정, 정밀도만) | GGUF-Q4_K_M / GGUF-F16 = 30.35 / 10.45 | **2.90배** |
| bitsandbytes 양자화 (HF 고정, 정밀도만) | HF-NF4 / HF-FP16 = 3.34 / 9.02 | **0.370배 (2.7배 느림)** |

**이 분해는 세 번의 독립 실행에서 재현됐습니다** — 서로 다른 밤, 서로 다른 기계 상태, 서로 다른 순서 배정에서:

| 실행 | 엔진 | K-quant | NF4 | 합계 |
|---|---|---|---|---|
| v3 (24GB, 스왑 포화) | 1.12배 | 2.89배 | 0.375배 | 3.23배 |
| v5 (24GB, 폐기된 실행) | 1.06배 | 3.05배 | 0.340배 | 3.25배 |
| **v6 (24GB, 감사 통과)** | **1.16배** | **2.90배** | **0.370배** | **3.36배** |
| v6 (16GB) | 1.14배 | 3.21배 | 0.368배 | 3.65배 |

"GGUF가 FP16보다 3.36배 빠르다"는 사실이지만 요인을 분리하면 대부분(2.90배)이 K-quant 양자화이고 엔진 자체 기여는 1.16배에 불과합니다. 같은 "4-bit"인데 llama.cpp의 K-quant는 2.90배 빨라지고 bitsandbytes NF4는 2.7배 느려지는 정반대 결과는, K-quant가 추론 전용으로 디퀀타이즈+행렬곱을 융합한 커널인 반면 NF4는 QLoRA 학습의 메모리 절감이 주목적이라 추론 시 디퀀타이즈 오버헤드가 대역폭 절감분을 상쇄하기 때문으로 보입니다(커널 단위 프로파일링으로 직접 검증한 건 아닌 아키텍처 지식 기반 추정).

VRAM 절감은 62%(7.54→2.88GB, HF NF4), perplexity 저하는 +2.8%(9.54→9.81)로 미미 — "메모리는 확실히 줄지만 속도는 대가를 치른다"가 bitsandbytes NF4의 요약입니다.

### Context-length scaling

프롬프트 128→4096 토큰의 decode tok/s, **24GB 대조군, 3회 반복 중앙값 [최소–최대]**:

| ctx | HF FP16 | HF NF4 | GGUF F16 | GGUF Q4_K_M |
|---|---|---|---|---|
| 128 | 9.02 [8.98–9.39] | 3.34 [3.32–3.35] | 10.45 [10.06–10.54] | 30.35 [14.08–30.62] |
| 512 | 8.01 [5.85–8.94] | 3.31 [3.29–3.32] | 10.26 [10.25–10.31] | 28.21 [28.16–28.29] |
| 1024 | 8.13 [7.70–8.26] | 3.15 [2.90–3.21] | 10.04 [9.10–10.14] | 26.19 [23.10–26.99] |
| 2048 | **1.90** [1.81–2.74] | 3.06 [2.64–3.10] | 9.59 [8.46–9.64] | 23.95 [23.52–24.00] |
| 4096 | 3.65 [1.59–5.33] | 2.22 [0.44–2.49] | 8.79 [7.76–8.88] | 19.41 [9.78–19.80] |

TTFT(prefill)는 네 설정 모두 컨텍스트에 거의 선형이라 4096에서 15.9~18.2초로 수렴합니다(C-1 수정 검증 — 버그 있던 v2는 HF TTFT를 0.03초로 보고했는데 4104토큰 prefill로선 물리적으로 불가능한 값이었습니다).

**저하폭 %는 오해를 부릅니다.** 128→4096 중앙값 저하: GGUF F16 −16%, Q4_K_M −36%, NF4 −34%, FP16 −59%. 순서만 보면 "GGUF F16이 가장 강건"이지만 **토큰당 절대 지연으로 보면 다릅니다**:

| Config | ms/token 128→4096 | 절대 증가 |
|---|---|---|
| GGUF F16 | 95.7 → 113.7 | **+18.0 ms** |
| GGUF Q4_K_M | 32.9 → 51.5 | **+18.6 ms** |
| HF FP16 | 110.8 → 273.7 | +162.8 ms |
| HF NF4 | 299.3 → 450.3 | +151.1 ms |

GGUF F16과 Q4_K_M은 **사실상 같은 절대 비용(+18.0 vs +18.6 ms/token)**을 추가합니다. F16이 −16%로 완만해 보이는 건 baseline이 느려서(95.7ms) 같은 손해가 작은 %로 나올 뿐입니다. 대역폭 바운드 디코딩의 roofline이 예측하는 결과입니다 — 토큰당 읽는 바이트 = 가중치 + KV 캐시이고, **KV 캐시 증가분은 가중치 정밀도와 무관**하므로 절대 지연 증가도 같아야 합니다. v3에서 +16.4 vs +17.8이던 것이 v6에서 +18.0 vs +18.6으로 더 가까워졌습니다. "GGUF F16이 왜 가장 강건한가"는 미스터리가 아니라 % 지표의 함정이었습니다.

같은 구간 Peak VRAM(HF만, 중앙값): FP16 7.54 → 8.22GB (+0.68), NF4 2.88 → 4.05GB (+1.17). NF4의 절대 증가가 더 큰 이유는 v1부터 미규명입니다([Limitations](#limitations)).

### 미해결: FP16 @2048 비단조 절벽

FP16만 1024 → 2048에서 **4.3배 급락**한 뒤 4096에서 부분 회복합니다. 같은 엔진의 NF4는 매끄럽게 내려가므로 FP16 경로 특이적입니다.

| 실행 | @1024 | @2048 | @4096 | 4096이 2048보다 |
|---|---|---|---|---|
| v3 (24GB) | 7.84 | **1.91** | 4.51 | 2.36배 빠름 |
| v5 (24GB) | 6.79 | **2.13** | 3.97 | 1.86배 빠름 |
| v6 (24GB) | 8.13 | **1.90** | 3.65 | 1.93배 빠름 |
| v6 (16GB) | 6.43 | **0.37** | 0.73 | 1.99배 빠름 |

**세 번의 독립 실행에서 소수점 둘째 자리까지 재현**되므로 노이즈가 아닙니다. v3가 붙였던 "스왑 변동" 설명은 반증됐습니다.

가장 강한 단서는 마지막 열입니다: 16GB에서 전체 속도가 5배 느려졌는데도 **2048:4096 비율은 1.93 → 1.99로 보존**됩니다. 메모리 압박이 원인이라면 압박을 키웠을 때 모양이 변해야 하는데, 전체를 곱셈으로 스케일할 뿐 모양은 그대로입니다 — **이 현상은 메모리 압박과 직교하며, 형상/커널 계열을 먼저 봐야 합니다.**

실용적 함의도 큽니다. 16GB에서 150토큰 생성에 프롬프트 2048은 **415초**, 4096은 **221초** — 입력을 두 배로 늘리면 프리필을 더 쓰고도 3분 이상 빨라집니다. 또한 이 구간에서 계산된 모든 비율이 오염됩니다(24GB ctx=2048에서 Q4_K_M/FP16 = 12.6배, 다른 구간은 3.2~5.3배). 이건 양자화 이야기가 아니라 FP16 병리 이야기입니다.

아직 **PyTorch/MPS의 현상인지 우리 하네스의 현상인지 구분되지 않았습니다.** 이 저장소는 이미 측정 결함을 네 번 잡았으므로, "재현되는 이상 현상"이 우리 코드였던 전적을 감안해야 합니다.

## 16GB: 실제 사람들이 쓰는 기계

24GB에서는 FP16 8GB가 여유롭게 들어가 벤치마크가 사실상 커널 효율만 잽니다. 주류 구성인 16GB에서는 다릅니다. 같은 프로토콜로 `--ballast-gb 8`을 걸어 재측정했습니다(3회 중앙값 [최소–최대]):

| ctx | HF FP16 | HF NF4 | GGUF F16 | GGUF Q4_K_M |
|---|---|---|---|---|
| 128 | 8.80 [7.80–9.02] | 3.24 [3.20–3.34] | 10.02 [9.92–10.47] | 32.12 [17.84–32.13] |
| 512 | 5.69 [3.76–7.65] | 3.09 [2.17–3.30] | 10.23 [9.30–10.88] | 24.62 [20.92–29.08] |
| 1024 | 6.43 [3.35–6.62] | 3.18 [3.09–3.38] | 10.31 [9.16–10.88] | 26.61 [22.78–27.54] |
| 2048 | **0.37** [0.36–0.72] | 2.63 [2.16–2.88] | 9.71 [8.35–9.73] | 22.65 [18.70–25.30] |
| 4096 | **0.73** [0.70–3.55] | 1.30 [1.08–1.53]† | 7.69 [5.72–8.36] | 17.10 [11.99–19.32] |

† n=2. 세 번째 반복은 2시간 넘게 thrashing해 중단했습니다(같은 셀의 다른 두 반복은 2.6분·3.3분). 측정 실패 자체가 결과입니다 — 이 조합은 때때로 회복 불가 상태에 빠집니다. 오염 방지를 위해 해당 행은 기록하지 않았습니다.

**24GB 대비 저하율:**

| Config | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| HF FP16 | −3% | −29% | −21% | **−81%** | **−80%** |
| HF NF4 | −3% | −7% | +1% | −14% | **−41%** |
| GGUF F16 | −4% | −0% | +3% | +1% | −13% |
| GGUF Q4_K_M | +6% | −13% | +2% | −5% | −12% |

**mmap이냐 상주냐로 범주적으로 갈립니다.** 컨텍스트 전 구간 최악 저하가 mmap 그룹 **−12.7%**, 상주 그룹 **−80.5%** — 연속 스펙트럼이 아니라 두 덩어리이고 사이에 아무것도 없습니다.

가장 결정적인 대비: **GGUF F16(가중치 8GB, mmap)이 HF NF4(가중치 2.9GB, 상주)를 압도합니다.** 3배 가벼운 모델이 3배 무거운 모델에게 집니다. 16GB에서 중요한 건 모델을 얼마나 줄였느냐가 아니라 **런타임이 메모리를 어떻게 잡느냐**입니다. 다만 상주 그룹 *내부*에서는 크기가 작동합니다 — FP16(8GB)은 2048에서, NF4(2.9GB)는 4096에서 무너집니다. 즉 2단 구조입니다: **1차 요인 mmap 여부, 2차 요인 가중치 크기.**

**roofline은 스왑 전까지만 유효합니다.** 128→4096 절대 증가를 16GB에서 보면 mmap 그룹은 여전히 붙어 있지만(GGUF F16 +30.3ms, Q4_K_M +27.4ms) 상주 그룹은 규모가 다릅니다(FP16 **+1247ms**, NF4 +458ms). 인사이트 ③은 틀린 게 아니라 **적용 범위가 있었던 것**입니다 — 스왑이 시작되면 다른 물리 법칙으로 넘어갑니다.

**실사용 관점 — 16GB에서 150토큰 생성 전체 소요(프리필 포함):**

| | 128 | 512 | 1024 | 2048 | 4096 |
|---|---|---|---|---|---|
| **GGUF Q4_K_M** | 5s | 8s | 9s | 15s | 27s |
| **GGUF F16** | 15s | 16s | 18s | 23s | 36s |
| HF NF4 | 47s | 51s | 51s | 66s | 132s |
| HF FP16 | 18s | 28s | 27s | **415s** | 221s |

16GB 맥에서 transformers FP16으로 2K 프롬프트를 처리하면 7분, 같은 작업이 llama.cpp Q4_K_M으로 15초입니다.

## Memory pressure (ballast 실험)

v1은 "다른 앱이 켜져 있어 스왑으로 붕괴"라는 재현 불가 일화로 "GGUF는 mmap 덕분에 강건"을 주장했습니다. v2에서 이를 통제 실험으로 만들었지만(ballast 프로세스로 메모리 강제 점유 + mmap on/off 대조), 두 가지 결함이 드러났습니다: (a) `ballast.py`가 초기 fill 후 64MB 창만 재기록하는 순회 버그로 나머지 ~99%가 스왑아웃돼 실제 압박을 유지하지 못했고, (b) 0GB 기준선이 이미 스왑 30GB로 오염돼 "유휴 vs 압박"이 아니라 "압박 vs 더-압박"이었습니다.

v3에서 도구는 완전히 고쳤습니다:
- `ballast.py` 순회 버그 수정(전 페이지를 매 주기 터치해 상주 유지 — 3GB 요청 시 RSS가 축소 없이 유지됨을 확인)
- `pressure_probe.py`에 **GGUF F16 추가**(8GB 가중치로 압박에 가장 취약한 후보), **config 순서 무작위화**(순서 교락 제거), **매 측정 시점의 실제 스왑 사용량 기록**(압박이 실제로 걸렸는지 조작검증), 다단계 ballast(0/8/16GB 양성 대조), 그리고 v3의 수정된 측정 경로(`measure_one`) 사용

**v4에서 재부팅 직후(스왑 0GB) `tools/pressure_probe.py --ballast-gb 0,8,16`을 실행했습니다**(`results/results_memory_pressure.jsonl`). 0→16GB ballast에서 decode tok/s 저하:

| Config | ctx=128 | ctx=4096 |
|---|---|---|
| GGUF Q4_K_M **(mmap)** | 30.96 → 31.02 (+0.2%) | 20.89 → 18.96 (**−9.2%**) |
| GGUF Q4_K_M **(nommap)** | 30.32 → 30.28 (−0.1%) | 20.74 → 12.49 (**−39.8%**) |
| GGUF F16 (mmap) | 11.09 → 10.63 (−4.1%) | 9.39 → 8.14 (−13.4%) |
| HF FP16 | 9.16 → 8.73 (−4.6%) | 2.44 → 0.97 (−60.4%) |
| HF NF4 | 3.49 → 3.41 (−2.4%) | 2.38 → 0.47 (−80.5%) |

- **단문(128)은 아무도 안 흔들립니다**(≤5%) — working set이 작아 압박은 장문에서만 뭅니다.
- **장문(4096)에서 mmap 가설이 직접 확인됐습니다.** 같은 Q4_K_M 가중치·엔진에서 `use_mmap`만 끄면 저하가 **−9.2% → −39.8%로 4.3배** 커집니다. 0GB에선 둘 다 ~20.8 tok/s로 같으므로 이 격차는 압박이 있을 때만 열립니다. **v2의 버그 있던 ballast가 "반증"했던 v1 mmap 가설이, 고친 도구·깨끗한 baseline에서 오히려 재확인된 셈입니다.**
- **이 `use_mmap` A/B는 v6가 대체하지 못하는 유일한 증거입니다.** 메인 스윕은 mmap을 끄지 못하므로, "GGUF가 강건한 건 llama.cpp라서가 아니라 mmap이라서"를 못박는 대조군은 여전히 여기에만 있습니다.

**⚠️ 이 표의 HF 수치는 v6가 갱신했습니다.** 위는 **반복 1회**라 셀별 신뢰구간이 없습니다. 3회 반복으로 다시 재보니 HF 두 경로의 **순위가 뒤집혔습니다**:

| ctx=4096, 24GB→16GB | v4 (n=1) | v6 (n=3) |
|---|---|---|
| HF FP16 | −60.4% | **−80%** |
| HF NF4 | −80.5% | **−41%** |

v4만 보면 "NF4가 FP16보다 더 무너진다 → 가중치 크기는 무관하다"로 읽히지만, n=3에서는 모든 컨텍스트에서 NF4가 FP16보다 낫습니다. 올바른 결론은 [16GB 절](#16gb-실제-사람들이-쓰는-기계)의 2단 구조입니다 — 1차 요인은 mmap 여부(NF4 2.9GB가 GGUF F16 8GB에게 짐), 2차 요인은 가중치 크기(상주 그룹 내에서는 작은 쪽이 더 오래 버팀). **단발 측정으로 순위를 매기면 안 된다는 사례로 남깁니다.**

("0GB" 기준선도 8GB F16 가중치를 로딩하며 세션 스왑이 6~7GB로 오르지만, 매 측정의 스왑을 기록해 드러냈고, mmap A/B는 두 config의 스왑이 비슷해 공정합니다.)

## Limitations

- **스윕이 자기가 측정하는 환경을 스스로 오염시킵니다.** 24GB 대조군은 스왑 132MB에서 시작했는데 실행 중 **13.4GB**까지 올랐고, 16GB 실행은 19.0GB까지 갔습니다(8GB 모델을 60번 로드/해제하며 파일 페이지 캐시가 통합 메모리를 채움). 전역 셔플이 이 드리프트를 *편향*에서 *분산*으로 바꿔 중앙값이 흡수하게 만들지만, **압박 자체가 사라진 것은 아닙니다.** 재부팅으로도 못 고칩니다 — 3회차는 시작 상태와 무관하게 다시 포화됩니다. 즉 "24GB 대조군"도 압박 없는 상태가 아닙니다.
- **ballast는 실제 16GB 기계보다 공격적입니다.** 매 주기 전 페이지를 훑느라 CPU를 ~36% 쓰고 대역폭도 소량 소비합니다. 실제 기계의 "다른 8GB"는 이렇게 능동적이지 않으므로 **상주 그룹 수치는 비관적일 가능성**이 있습니다. 또 macOS는 압축기 풀·캐시 크기를 *물리* RAM 기준으로 잡으므로 ballast 16GB ≈ 실제 16GB이지 동일하지는 않습니다.
- **3회 반복 기준**이며 NF4@4096(16GB)은 n=2입니다(3회차 2시간+ thrashing으로 중단). 변동이 큰 셀은 반복을 더 늘려야 합니다.
- **CUDA 교차검증은 v1 버그 방식이라 제외**했습니다(`results/results_cuda_t4_colab_v1_double_prefill_bug.jsonl`). C-1은 CUDA도 비동기라 동일 발현하므로 현 프로토콜로 재측정해야 유효합니다. **현재 결론은 전부 Apple Silicon 통합 메모리 기준**이며, mmap 우위가 별도 VRAM을 가진 GPU에서도 성립하는지는 미검증입니다.
- **모델 크기는 설계가 강제한 것입니다.** 2×2의 FP16 팔이 성립하려면 FP16 가중치가 16GB에 들어가야 하고, 4B(~8GB)는 그 조건을 만족하는 최대 크기입니다(7B는 ~14GB, 8B는 ~16GB로 불가). 따라서 **실사용자가 16GB에서 실제로 돌릴 구성(7~14B의 4비트)과는 다릅니다** — 이 리포트의 목적은 요인 분해이지 기종별 최적 모델 추천이 아닙니다.
- **MPS Peak VRAM은 20ms 폴링 근사**로 짧은 스파이크를 놓칠 수 있습니다. NF4의 절대 VRAM 증가가 FP16보다 큰 원인은 미규명입니다.
- **GGUF 경로는 매 측정 워밍업 후 `llm.reset()`으로 캐시를 비워** 매번 완전한 prefill을 강제합니다 — 접두사가 재사용되는 실사용 멀티턴 대화보다 보수적(불리한) 조건입니다.
- **속도 지표는 커널 프로파일링이 아닌 end-to-end 측정**입니다. NF4가 느린 원인(디퀀타이즈 커널 융합 부재)은 아키텍처 지식 기반 추정입니다.
